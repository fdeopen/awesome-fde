# PoC：降低关键不确定性

PoC 的目标不是证明“可以做出一个界面”，而是用有限时间和预算验证最可能让生产系统失败的假设。

## PoC 章程

使用 [PoC 章程模板](../templates/poc/poc-charter.md) 明确：

- PoC 结束后要做的决策：继续、调整、缩小或停止
- 1–3 个关键假设，每项对应证据、阈值和负责人
- 用户、数据、功能、系统、时间和预算边界
- 高频、长尾、高风险和对抗性真实任务样本
- 当前人工流程或现有系统的同口径基线
- 质量、业务、风险、延迟、成本与人工审核指标
- 代码、评估集、日志、结论和未决风险等退出材料

## 执行原则

1. 一次 PoC 只验证少量关键假设。
2. 使用真实或经授权脱敏的数据分布，不使用精选演示题。
3. 每项成功标准都必须写成可以失败的句子。
4. 每周展示进展、失败样本、风险和下一步，不隐藏坏消息。
5. 同时记录进入生产仍缺少的身份、权限、日志、回退和运营控制。

## 结束结论

| 结论 | 适用情形 | 后续动作 |
| --- | --- | --- |
| 进入有限生产 | 核心假设通过，剩余风险可控 | 补齐生产门禁并灰度上线 |
| 调整后复测 | 局部假设失败但有可验证改进路径 | 修改流程、数据或模型后复测 |
| 缩小范围 | 价值存在，但权限、成本或风险限制明显 | 降低自主性或减少用户/数据范围 |
| 停止 | 价值、采用、数据、风险或经济性不成立 | 安全归档资产与失败知识 |

停止不是失败。无法说明价值和边界却无限迭代，才是失控。
